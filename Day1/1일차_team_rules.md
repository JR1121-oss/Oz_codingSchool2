## 1️⃣ ☝🏻 소통 및 회의 규칙 (Communication)

## 2️⃣ Git & GitHub 버전 관리 규칙 (Version Control)

> 코드 충돌을 최소화하고 변경 이력을 체계적으로 관리하기 위한 규칙입니다.

- **브랜치 전략:** `main`에 직접 푸시하지 않고, `develop`에서 개인 작업 브랜치를 생성하여 작업한다. PR을 통해 `develop`에 병합한다.

- **작업 순서:** 최신 `develop`에서 브랜치를 생성하고, 작업 후 변경 사항을 동기화한 뒤 PR을 생성한다.

  ```bash
  git switch develop
  git pull origin develop
  git switch -b feature/기능명_YYMMDD

  # 작업 후 develop 동기화
  git switch develop
  git pull origin develop
  git switch feature/기능명_YYMMDD
  git merge develop

  # 커밋 및 업로드
  git status
  git add <파일 경로>
  git commit -m "[Feat] 기능 설명"
  git push -u origin feature/기능명_YYMMDD
  ```

- **코드 리뷰:** PR 병합 전 팀원 최소 1명의 리뷰와 승인을 받는다. 본인이 작성한 PR은 직접 승인하지 않는다.

- **커밋 메시지:** 작업 유형을 태그로 표시한다.
  - `[Feat]` 기능 추가 / `[Fix]` 버그 수정 / `[Docs]` 문서 수정
  - `[Refactor]` 코드 개선 / `[Test]` 테스트 추가 및 수정

- **변경 사항 확인:** 커밋 전 `git status`로 확인하고, 관련 파일만 선택하여 커밋한다.

- **민감 정보 보호:** API 키, 비밀번호, `.env` 등 민감 정보는 업로드하지 않는다.

- **공용 코드 보호:** 협의 없이 강제 푸시하거나 다른 팀원의 변경 사항을 덮어쓰지 않는다.

- **1일 1커밋 (선택):** 꾸준한 작업 기록을 위해 하루 1회 커밋 및 푸시를 권장하되, 의미 없는 커밋은 지양한다.

## 3️⃣ 일정 및 과제 관리 규칙 (Task Management)
>작업 진행 상황을 공유하고 마감일까지 과제를 체계적으로 완수하기 위한 규칙입니다.

- **작업 분배 및 공유:** 매일 오전 또는 회의 시간에 당일 할 일(To-Do)과 담당자를 공유한다.

- **진행 상황 업데이트:** Notion, Trello 등 팀에서 합의한 칸반보드에 작업 상태를 업데이트한다. (예: 할 일 → 진행 중 → 완료)

- **이슈 발생 시 즉시 공유:** 오류가 해결되지 않거나 작업이 지연될 경우 혼자 해결하려고 오래 붙잡고 있지 말고, 코어 타임이나 회의 시간에 팀원에게 공유한다.

- **작업 지연 사전 공지:** 담당 작업이 일정 내 완료되기 어려울 것으로 예상되면 미리 공유하고 일정 및 역할을 조정한다.

- **작업 결과 기록:** 작업 완료 후 변경 사항, 해결 방법 및 남은 이슈를 간단히 기록하여 팀원이 확인할 수 있도록 한다.

## 4️⃣ 협업 시 공통 원칙 (Collaboration)

- **작업 범위 준수:** 담당 작업과 수정할 파일을 사전에 확인하고, 다른 팀원의 담당 영역을 변경해야 할 경우 먼저 협의한다.

- **충돌 발생 시 협의:** Merge Conflict가 발생하면 변경 내용을 확인하고 관련 팀원과 협의하여 해결한다. 내용을 이해하지 못한 상태에서 임의로 삭제하거나 덮어쓰지 않는다.

- **소통과 피드백:** 코드 리뷰 및 의견 공유 시 상대방을 존중하고, 수정이 필요한 이유와 개선 방향을 구체적으로 전달한다.

- **공유 저장소 기준 준수:** 브랜치명, 커밋 메시지, PR 작성 및 병합 방식은 팀에서 합의한 규칙을 공통으로 적용한다.
