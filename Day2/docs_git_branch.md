# Git & GitHub Flow Branch 전략

## 1. Git Branch 전략이란?

> Git Branch 전략은 여러 개발자가 하나의 저장소에서 협업할 때, 브랜치의 생성·사용·병합 규칙을 정하고 효율적인 개발 작업 흐름(Workflow)을 정의하는 것이다.

## 2. Git Branch 전략이 필요한 이유

> 여러 개발자가 동시에 작업할 때 각자 담당하는 기능이나 수정 사항을 독립적인 브랜치에서 개발하면 서로의 작업에 미치는 영향을 줄일 수 있다.

- **독립적인 개발:** 기능별로 브랜치를 분리하여 동시에 작업할 수 있다.
- **충돌 방지:** 작업 내용을 분리하여 코드 충돌과 작업 간 간섭을 줄일 수 있다.
- **안정성 확보:** 검토와 테스트를 거친 코드를 기준 브랜치에 병합할 수 있다.
- **협업 효율 향상:** 브랜치 생성, 코드 리뷰, 병합 등의 규칙을 통일하여 협업 과정을 체계화할 수 있다.

## 3. 대표적인 Git Branch 전략

> 대표적인 브랜치 전략으로는 **Git Flow**와 **GitHub Flow**가 있다.

| 구분 | Git Flow | GitHub Flow |
|---|---|---|
| 특징 | 브랜치 역할을 세분화한 전략 | 단순하고 가벼운 전략 |
| 적합한 환경 | 정기적인 릴리스와 여러 배포 단계가 있는 프로젝트 | 지속적인 배포가 이루어지는 웹 서비스 |
| 주요 브랜치 | `main`, `develop`, `feature`, `release`, `hotfix` | `main`, `feature` |
| 개발 및 병합 | 개발·릴리스·긴급 수정 단계를 구분 | 기능 브랜치에서 개발 후 PR을 통해 `main`에 병합 |
| 배포 방식 | 릴리스 준비 및 QA 단계를 거쳐 배포 | `main`에 병합한 후 배포하는 방식이 일반적 |

### 3.1. Git Flow

> Git Flow는 개발, 릴리스 준비, 운영 배포, 긴급 수정 등의 단계를 구분하여 관리하는 브랜치 전략이다. 정기적인 배포 일정이 있거나 여러 단계의 테스트 및 검증이 필요한 프로젝트에 적합하다.

#### 주요 브랜치

| 브랜치 | 역할 |
|---|---|
| `main` (또는 `master`) | 사용자에게 배포되는 안정적인 제품 코드를 유지한다. |
| `develop` | 다음 릴리스를 위해 개발된 기능을 통합한다. |

#### 보조 브랜치

| 브랜치 | 역할 |
|---|---|
| `feature` | 새로운 기능을 개발하며, 일반적으로 `develop`에서 생성한다. |
| `release` | 릴리스에 포함할 기능을 확정한 후 배포 전 QA 및 버그 수정을 진행한다. |
| `hotfix` | 운영 중인 제품에서 긴급한 버그가 발생했을 때 수정하며, 일반적으로 `main`에서 생성한다. |

#### 기본 작업 흐름

1. `develop`에서 `feature` 브랜치를 생성하여 기능을 개발한다.
2. 개발이 완료되면 `feature`를 `develop`에 병합한다.
3. 배포할 기능이 확정되면 `develop`에서 `release` 브랜치를 생성한다.
4. `release`에서 QA 및 필요한 버그 수정을 진행한다.
5. 검증이 완료되면 `release`를 `main`에 병합하여 배포한다.
6. 운영 중 긴급한 버그가 발생하면 `main`에서 `hotfix` 브랜치를 생성하여 수정한 뒤, 수정 사항을 필요한 브랜치에도 반영한다.

### 3.2. GitHub Flow

> GitHub Flow는 브랜치 구조를 단순화하여 빠른 개발과 지속적인 배포를 지원하는 전략이다. CI/CD가 적용된 프로젝트나 수시로 배포하는 웹 서비스에 적합하다.

#### 주요 브랜치

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 배포 가능한 상태를 유지하는 기준 브랜치이다. |
| `feature` | 새로운 기능 개발이나 버그 수정을 위해 `main`에서 생성하는 작업 브랜치이다. |

#### 기본 작업 흐름

1. `main`에서 새로운 `feature` 브랜치를 생성한다.
2. 해당 브랜치에서 기능 개발 또는 버그 수정을 진행한다.
3. 작업 내용을 원격 저장소에 `push`한다.
4. Pull Request(PR)를 생성하여 변경 사항을 공유하고 코드 리뷰를 진행한다.
5. 검토 및 필요한 테스트가 완료되면 PR을 통해 `main`에 병합한다.
6. 병합된 코드를 배포한다. 자동 배포를 적용한 프로젝트에서는 병합 후 배포가 자동으로 진행될 수 있다.

## 4. Git Flow와 GitHub Flow의 핵심 차이

- **Git Flow:** 개발과 릴리스, 운영 배포 단계를 분리하여 체계적으로 관리한다.
- **GitHub Flow:** 작업 브랜치와 PR 중심으로 개발 과정을 단순화하고 빠르게 배포한다.

> 프로젝트의 배포 주기, QA 단계, 협업 규모 및 운영 환경에 따라 적합한 전략을 선택할 수 있다.
